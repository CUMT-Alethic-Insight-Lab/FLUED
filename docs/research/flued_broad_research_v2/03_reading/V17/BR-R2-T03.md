## Problem and algorithm

Existing pipelines process special-token segments, regular-expression pretokens and byte-pair-encoding (BPE) merges mostly in stages. The problem is to emit offline-equivalent tokens incrementally from arriving text without prematurely committing a token invalidated by future characters (§1.1, §4). This is an algorithmic interface for language models, not learned segmentation, memory addressing, nor a neural objective; the BPE merge list is previously trained/fixed. Input units in the theorem are alphabet characters; emitted tokens may encode multiple bytes/characters. UTF-8 partial-byte transport is not independently analysed, and theorem assumptions do not automatically establish a production incremental decoder.

At input prefix x, a stable token prefix must remain a prefix of Tok(xy) for **every** possible continuation y (including empty). The ideal online comparator Tok≤(x) is its longest stable prefix. Delay k means Tok≤(x without last k input characters) ≤ output ≤ Tok≤(x), not wall-clock latency or k emitted tokens (Def. 4.7–4.9). End-of-input makes the remaining offline suffix computable by a final flush, but stable-prefix behavior before end-of-file is a different query; no quoted TTFT establishes GPU prefill/decode speed.

## Results and proof boundaries

Under total regex R, canonical merge list M of m rules, longest token length t, and fixed finite alphabet/special-token set, Theorem 1.1 claims polynomial-preprocessing/total-time exact zero-delay tokenization, and o(mt) delay, are impossible unless P=NP (pp. 3, 13–16). This is a parameterized worst-case family with regex/dictionary growing, **not** that a particular fixed practical tokenizer or each input is NP-hard. A constructive 3-SAT reduction uses future continuations to change the stability of one token; the delay extension pads a long unresolved region (§4.1).

Theorem 1.2's component composition achieves O(n log²t) time, O(b(R)+mt) space and b(R)+(m+1)t+longest-special-token delay, with b the regex lookback. Theorem 1.6 gives an adversarial case R=a^f b | a | b, M=[bb→B], input a^f: separate pretokenization waits although final BPE output is already stable (§4.3). Theorem 1.7 combines data structures for pretoken boundaries and BPE first tokens, claiming O(mt) preprocessing and delay, O(n(log²t+log m+log min(n,b))) total time, O(min(n,b)+mt) space (§5); constants suppress regex and special-token factors. This is optimal in asymptotic **delay versus the stated worst-case conditional comparator**, not optimal wall-time or constant space for arbitrary regex. Appendix A provides omitted suffix-query proof; no independent proof certification.

## Experimental controls, negative cases, cost

Single Intel Xeon Platinum 8462Y+ core, idle host; 20231101 Wikipedia English/Chinese samples and RedPajama GitHub code, approx 128 MiB throughput inputs; reference encodings r50k/p50k/cl100k/o200k and several HuggingFace tokenizers (§6–7). Authors report identical output vs references on datasets and many short strings, plus regex simplification/fixup equivalence proof for three patterns (§6.3); this is not an exhaustive validation of every library mode, normalization or arbitrary byte stream.

Printed Table 1: first-token-formed speedup versus better of tiktoken/gigatoken is 7.9–34.8×. Table 3 measures 30-run medians; baseline receives in-memory string and patched instrumentation while proposed implementation includes file reading; TTFT means **first formed**, not downstream delivered. Table 2/4/5 report 2.4–7.0× throughput over tiktoken and 15.8–38.1× over tokenizers on their selected encodings; 10-run medians, tokenizer initialization excluded, file output backed by memory (§7). In Table 6 optimized serial gigatoken array output wins on English and several code encodings (e.g. r50k English 331.1 vs 298.7 MiB/s), so no universal throughput superiority. On measured 1–128 MiB inputs memory is approximately flat, but Fig. 2 shows initialization makes its RSS higher than tiktoken on small inputs.

Crucially practical code uses simple backtracking and **waits for a completed pretoken before BPE**, unlike the proven low-delay construction (§6.2 pp. 40–41): unfinished pretokens can grow arbitrarily, so observed flat RSS is not a worst-case guarantee. CL100K/O200K generalized lookback is unbounded for adversarial whitespace (§6.1). Special tokens, flush, Unicode boundaries, transport chunks, and alternative pretokenization require own exactness tests. Paper discloses generative AI use for theory design/code; the tokenizer mechanism itself is deterministic (§7, statement on AI usage).
