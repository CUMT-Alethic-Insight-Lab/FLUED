# W0438 — Mooncake: A KVCache-centric Disaggregated Architecture for LLM Serving

**Problem → solution.** Diverse long-context requests create expensive prefill, repeated KV construction, network hot spots and overload. Mooncake borrows disaggregated resource pools, prefix-hash caching, distributed scheduling, replication and asynchronous pipelining: place reusable K/V in CPU DRAM/SSD across the cluster, select prefill/decode nodes, stream layerwise K/V, and reject predicted infeasible work early. No model learning objective; predictive scheduling is based on offline timing profiles and system-level load estimates, not learned semantic retrieval.

**Contract (§§2–7).** 512-token prefix blocks keyed by a cumulative token-prefix hash; query is exact prefix identity, content is model-layer K/V, not an external-text search result. Reuse, recomputation, eviction (LRU/LFU options), hotspot replication and transfer compete with latency objectives. New raw prompt may be recomputed if cache unavailable; caller/source supplies prompt. Prefill/decoding pools can exchange data using RDMA and CPU memory while GPU computes. A two-stage check can reject after prefill, wasting compute; prediction-based early rejection estimates future decoder load using uniform request duration, not exact output lengths. Hash identity alone does not establish model-version keys, changed-source invalidation, physical deletion or backup behavior; these are unknown in this report, not false claims.

**Evidence and cost (§§4, 6, 8).** Trace is a one-hour sampled 23,608 requests retaining arrival, length and remapped block hashes, not text. Average input 8,590, output 182 tokens. LRU hit rate 0.34 at 1,000 blocks and 0.55 at 50,000/infinite (Table 1); over half of blocks never reused in sample. Experiments replay traces using a **dummy LLaMA2-70B-shaped model**, not measured answer quality. Nodes have eight A800-80GB GPUs, up to 800Gbps RDMA. Four-node 3-prefill+1-decode vs four vLLM nodes achieves reported 20% and 40% greater SLO-constrained throughput on arXiv summarization and L-Eval; 2P+2D has worse TTFT than alternatives in those cases. Simulated 16k–128k throughput gains 50–525% occur under stated baseline handling, not universal hardware speedup. Real-trace replay 10P+10D versus 20 vLLM nodes yields reported ~75% more completed requests at TTFT 30s/TBT 0.1s/token; no actual semantic response equivalence measured. At 2× replay overload, Table 3 reports 4,183 baseline, 3,771 early and 3,589 prediction-early rejected of ~23k. CPU/DRAM/SSD/network utilization, full cost, cold p99 and version-refresh costs are not comprehensively charged. Paper's 'underutilized' capacity is not literally free.

**Inference/reversal.** Same-quality, same traffic, model/version and strict budget are needed to compare resident cache, external source recomputation and no-revisit state. Source-free state reform and better native queries are independent options. Low prefix reuse, cache contention, stale blocks, rejection outcomes or network bottlenecks can overturn projected savings; report all failed/rejected requests, not only completed. Directions R.09–R.10, R.16, I.26.
