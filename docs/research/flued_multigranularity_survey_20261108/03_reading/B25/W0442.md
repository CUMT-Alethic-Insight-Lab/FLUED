# W0442｜WiscKey: Separating Keys from Values in SSD-conscious Storage

- **状态：FULL**。Lanyue Lu、Thanumalayan Sankaranarayana Pillai、Andrea C. Arpaci-Dusseau、Remzi H. Arpaci-Dusseau，FAST 2016，[USENIX PDF](https://www.usenix.org/system/files/conference/fast16/fast16-papers-lu.pdf)。补读PDF第9–14页§4–6及各图注/表，无论文附录；图线未逐点数字化。本文未指定自有外置关键证明；未运行代码或复现实验。
- **续读关键负例**：PDF第11页/印刷p.142 §4.1.2–4.1.4：随机加载100GB库后扫描4GB，64B值时WiscKey比LevelDB慢12倍，设备并行随机读取成为瓶颈；GC期间，全部待清项均失效时吞吐下降约10%，其他所测空闲比例约降35%。ALICE在ext4/xfs/btrfs配置模拟3000余次选定崩溃未报新不一致，不等于对所有硬件/崩溃形式证明安全。1KB值最坏恢复实验LevelDB 0.7秒、WiscKey 2.6秒。
- **宏观负载与资源**：印刷p.143–144 §4.1.5–4.2，未回收失效值占空间；1KB值的范围扫描CPU使用率WiscKey 30.1%、LevelDB 11.2%。YCSB中RocksDB默认配置、LevelDB及WiscKey对照，WiscKey包括持续GC臂；短范围和Zipf缓存解释为何其结论不同于长顺序扫描。
- **地址与载荷**：§3.2–3.3，键和`(vLog偏移,值长度)`进入LSM树，值及对应键追加值日志；读键后再访问值，不能把指针当已读取内容。无训练、无query答案提前可见；操作粒度是键、值、日志块/文件，而非语义摘要。
- **来源生命周期**：删除仅删LSM键，旧值仍留vLog直到回收；回收扫描尾部片段并查索引，搬迁仍有效值至日志头、更新地址。顺序为新值fsync，再同步写新地址和tail，最后释放旧空间（§3.3.2）。崩溃恢复依赖作者描述的文件系统追加前缀性质、地址范围/键校验及同步写合同，不能直接推广为任意存储环境或可靠物理擦除。
- **成本/反例**：§3.3.1范围扫描的值不再排序，需随机读取并以32线程预取掩盖开销；§1作者明确小值随机写入后的大范围顺序扫描可能慢于LevelDB。§4设备为500GB Samsung 840 EVO、64GB内存，不能推为通用硬件结果；后半实测和GC开销见上；未报告所有冷/热缓存及完整源生命周期成本。
- **决策影响**：同源总空间/写入、GC搬迁、冷随机读、范围访问、删除残留和崩溃一致一并记账；若指针节省被载荷回访与清理抵消，不能仅凭小索引决定方案。
