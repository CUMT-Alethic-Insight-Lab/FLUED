## Units, method, and actual sharing

Input and target are bytes; boundary predictor creates variable-length latent segments, mean-pools causal encoder states, and a deep causal Transformer models segments. A Gumbel-sigmoid boundary signal and a rate-range auxiliary penalty train boundaries jointly. The next-byte head adds byte-encoder residuals and predicts x[t+1]; the separate multi-byte (MBP) Transformer receives duplicated, upsampled *previous-segment* latent outputs plus a downsampled segment residual and is supervised at x[t+2]. The segment attention mask permits self, preceding positions of the same segment, and the preceding segment; same-segment inputs are duplicates of past-segment information, not future true bytes (§§2–3, Fig.2). Thus attending to earlier slots is not conditioning on their sampled byte identities. The first byte is the normal autoregressive head; the remaining candidates are parallel conditional predictions, not a within-block autoregressive joint.

**Weight axes:** the two decoder heads share one vocabulary unembedding matrix (§3 p.4); their transformer layers are separate. Input embedding ↔ output tying is not specified. No inference from head-sharing to all layers or embedding tables. The architecture supplies one MBP decoder instead of a separate offset head per predicted byte; allocation of depths changes when matching total parameters, so this is not proof that adding MBP to a fixed existing network costs zero parameters.

**Objective:** weighted next-byte cross-entropy + MBP cross-entropy + boundary-rate loss (Eq.2); λ0=1, λ1=1, λ2=10 pretraining. The causal encoder sees only observed prefix. Algorithm 1 recomputes/updates segment trunk on a predicted boundary or missing cached state; otherwise reuses it. Prompt initializes from an already observed byte prefix; edge cases for partially filled segments, EOS, complete tensor indices and cache implementation are not fully specified. Algorithm's stated number of candidates and slices have index ambiguities; no code audit.

## Atomic findings / BIP links

- [BIP-0032](../../02_inventory/DETAILED_INVENTORY.md#BIP-0032): Serial byte output remains expensive even with compressed trunks. Solution: use a segment-aligned, single boundary-masked MBP decoder. MLP-MBP uses separate future-offset MLPs; model comparison controls total parameter count, not training FLOPs. Fig.3 finds LCA on the performance/throughput frontier on three of four plotted tasks, not unqualified wins.
- [BIP-0033](../../02_inventory/DETAILED_INVENTORY.md#BIP-0033): Confident parallel candidates can be wrong. Threshold policy accepts the first next-byte token, then only the left-to-right MBP prefix with probabilities ≥τ; it is **not exact sampling**. On five tasks Table 1 MLP candidate acceptance is 58.08–65.01%, LCA 45.95–51.68%, while LCA typically performs better at comparable throughput; confidence/acceptance alone is not quality. Fig.4 lowering τ .9→.7 raises acceptance 50.1→56.7%, increases throughput about 10%, but lowers mean task metric about 3 points. At τ=.75, n=3→7, DailySum throughput 210.42→164.18 bytes/s (App. B Table 3), contrary to an unconditional 'more candidates are faster' claim.
- [BIP-0034](../../02_inventory/DETAILED_INVENTORY.md#BIP-0034): Verification can preserve a *named* autoregressive reference rather than threshold approximation. Self-verification targets the LCA next-byte head; external verification targets a separately resident FlexiTokens (FxT) model. §6.3/Fig.8 report 2.1–2.3× external speedups at n=7 across three tasks, same-size draft and verifier; figure compares outputs/task scores and invokes standard speculative acceptance, but code and exact transformed proposal probabilities are not independently checked. App.B explicitly says **all speculative-acceptance results drop KV caching**; this is not cached serving evidence, and external model residency/memory and precision are unreported. App.B Table 5 reports self 45.85–46.36% and external 47.97–52.04%, but adjacent prose says 78–84%: source contradiction, not reconcilable here. Figure 6 reports 29–37% throughput increase from n=3 to n=7/8 under verification; Fig.7's 100-step sample averages 3.05/6 accepted.
